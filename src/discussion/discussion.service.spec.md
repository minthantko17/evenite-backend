## General Guidelines

* **Test ID:** Use a unique identifier for each test case.
* **Scenario:** Clearly describe what is being tested and the relevant condition.
* **Input:** List all parameters, mock values, fixtures, and required setup.
* **Expected Result:** Describe the behavior or output that should occur.
* **Actual Result:** Record the behavior or output observed during execution.
* **Test Result:** Use `Pass`, `Fail`, or another agreed status.
* Keep descriptions concise and consistent across test cases.
* For optional dependencies, explicitly state whether the dependency is **provided** or **not provided**.
* Keep the **Expected Result** and **Actual Result** structurally comparable so differences are easy to identify.

### Appendix B: Design note — per-test-case mock values

Unlike a single shared `MOCK_RETURN_MESSAGE` / `MOCK_ROOM_READ_STATUS_DTO` reused verbatim across ORGANIZER and PARTICIPANT scenarios, each test case that asserts on a `result` now mocks its own distinct return value (different `id`, `sender`, or `lastReadAt`) local to that test. This closes a class of false positive where a service bug that swaps `organizerProfileId`/`participantProfileId` between call arguments would still pass, because the mocked return value did not vary based on which identity was actually passed in. `toHaveBeenCalledWith` assertions on the mock call arguments remain the primary correctness check; the per-test return values are an additional guard on `result`.
